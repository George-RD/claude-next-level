# Pushback patterns

Push back when feedback is wrong, harmful, out of scope, unverifiable, or conflicts with user/project decisions.

Good pushback has:

- concise technical reason
- evidence from code, tests, docs, or commands
- an alternative path or explicit ask

Templates:

- "I checked <path/test>. This suggestion would break <behavior>. I recommend <alternative>."
- "This overlaps <spec/phase>. I will not implement it here; I can add a scope note or create a follow-up."
- "I cannot verify this without <missing input>. Should I investigate that first?"
- "The current implementation is intentional because <constraint>. The real issue is <smaller fix>."
